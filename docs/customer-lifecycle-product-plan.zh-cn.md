# SiftGate 产品化升级要点

> **第一次能用，下一次敢更。**
> 把“部署成功”升级为“客户能独立激活、使用、升级、恢复”的完整体验。

- 状态：**方案草案，未实施**；供产品与工程评审，不代表新增能力已经上线。
- 基线：2026-10-08，已发布的 v2.11.7 / `e3e8697`。
- 本次范围：产品定义、关键交互、技术边界、优先级与验收要点。
- 本次不做：改运行代码、修改密码、迁移数据、发布新版本或重启 2099。

## 01｜先回答：客户装好后的密码是什么？

**用客户安装器全新初始化的实例，没有统一默认密码。** 安装器为每台实例生成独立随机密码，在配置中保存 bcrypt 哈希，并将初始明文写入仅安装用户可读的文件。默认目录下，客户在自己的服务器执行：

```bash
cat "$HOME/siftgate/config/initial-admin-password.txt"
```

自定义安装目录时替换前缀。密码不要发到聊天或工单；妥善保管后可删除提示文件。它不是自动消费的一次性激活码，删除文件也不会使密码失效；备份不包含该明文提示文件。

**不能把这条路径当作所有安装方式的通用答案：**

| 安装/登录方式 | 当前行为 | 注意事项 |
|---|---|---|
| 客户安装器全新安装 | 随机密码写入实例的初始密码文件 | 不使用 `admin`、`123456` 或统一厂商口令 |
| 已有配置或旧实例迁移 | 沿用原有认证配置 | 本机旧 2099 不能假定使用新安装器的密码 |
| 从备份恢复 | 保留原有认证配置，不恢复初始明文提示文件 | 不要重新 `init` 覆盖已有实例来“找回密码” |
| 直接启动、认证开启且未配置本地密码/SSO | 应用仍有自动生成密码并写启动日志的后备路径 | 应纳入 P0 清理，不能将密码继续进入日志链路 |
| OIDC 登录 | 使用企业身份系统 | 复用已有能力，不重复建设另一套企业身份系统 |

用户截图的 `Invalid password` 只能证明登录失败，不能据此判断密码、安装方式或是否访问了正确实例。它暴露的是：页面没有解释凭据从哪里来、如何首次激活、忘记密码怎么办。

## 02｜产品定位：不要再交付一个“需要问运维的登录框”

建议以 **SiftGate Launchpad + 运维控制台** 组织这次升级，而不是往登录页堆按钮。

| 已有基础，可复用 | 下一步需要产品化 |
|---|---|
| 随机初始密码、密码哈希、登录限流、OIDC、工作空间成员能力 | 首次认领、管理员设置、可理解的登录状态、安全恢复、身份生命周期 |
| 固定 digest 镜像、原生双架构发布、安装校验、CLI 升级 | 后台版本中心、独立升级执行器、维护窗口、安装工具自身更新 |
| 默认 SQLite 校验备份、独立目录恢复、受限看门狗 | 恢复中心、恢复演练证据、数据库分型、清晰的失败处置 |

**设计原则：** 默认安全；客户自己决定何时变更；状态必须有证据；复杂性由产品承担，权限与风险仍由操作者确认。

## 03｜六个产品化模块

### A. Launchpad｜首次认领与上手 · P0

**客户看到：** “欢迎使用 SiftGate。先认领这台实例，再创建管理员。”

流程：环境预检 → 验证激活码 → 设置管理员凭据 → 确认工作空间/时区 → 接入首个供应商 → 生成最小权限 API Key → 验证首个请求。

- 安装器生成短期、单次使用且绑定实例的激活码，不再把长期随机密码当作正常交付体验。
- 激活必须原子化：并发浏览器只能完成一次；过期后由具备主机权限的操作者重新签发。不能让第一个访问网页的人抢占实例。
- 激活码只通过受控本机交付通道提供，不进入普通日志、URL 查询参数、分析系统或支持包。
- 新实例与旧实例显式区分。已有密码、SSO 或业务数据的实例，不因“用户表为空”而重新进入认领流程。
- 接入测试先说明会发送请求、可能产生供应商费用，由客户主动确认；不自动调用真实模型。
- 时区与预算周期首次明确选择，日后修改必须单独说明影响。

**体验加分：** 步骤可恢复、完成状态有实际证据、供应商接入后即给可复制的调用示例，而不是把用户丢到空仪表盘。

### B. Identity Center｜登录、密码与恢复 · P0 → P2

**客户看到：** 正常登录、企业登录、首次激活、管理员恢复四种清晰状态，而不是一条孤立的英文错误。

- 登录页提供密码可见切换、Caps Lock 提醒、密码管理器/粘贴支持、七语言错误码映射。
- 提示“请确认实例地址”，不假装能知道用户的密码属于另一台实例；未认证页面只显示必要的实例名称，不泄露系统细节。
- 已登录修改密码要求重新认证；遗失密码走本机受控恢复或已配置的企业身份恢复。未配置邮件就不显示不可用的“邮件找回”。
- 重置后撤销管理会话，但不得重置 Gateway API Key、供应商密钥、请求记录和计价数据。
- 必须显式设计会话撤销：当前安装器设置了独立 `session_secret`，不能假定“只改密码哈希就让所有旧 JWT 失效”。
- 保留旧共享密码兼容入口，逐步迁移到独立管理身份；角色与升级权限不能只靠一个共享 `dashboard` 身份冒充审计。
- 企业阶段复用 OIDC 与现有成员/角色能力，优先由 IdP 提供 MFA；本地强认证与紧急管理员入口单独设计和审计。

**体验加分：** 失败时给出下一步；恢复的是访问能力，不是明文原密码。所有生成密码的启动日志后备路径必须一起治理。

### C. Release Center｜可信版本与受控升级 · P1

**客户看到：** 当前运行版本、可升级版本、变更摘要、兼容范围、备份状况、预计中断范围，以及“安排维护窗口”。

- 可以自动检查/预下载；默认不自动重启，不因为 main 更新就更新客户。
- 使用可验证的发布元数据与固定 digest，显示 Gateway、安装工具、Operator、数据库 schema 各自版本。
- 新版不仅是镜像：安装脚本、Compose、Operator 与 schema 也要有兼容矩阵、分阶段更新和恢复点。当前 `upgrade` 不会自动替换宿主工具，必须补齐这条链路。
- 有数据库迁移时标明支持的源版本、是否可逆、是否必须停机。每次正式发布都要做真实跨版本演练；同代码镜像替换不等于跨版本兼容。
- 预检结论有有效期；执行前重查磁盘、备份能力、当前版本、实例身份与计划 digest。
- 页面刷新/关闭不取消已确认的任务；重复点击只产生一个操作；显示真实阶段和原因，不使用虚构进度或固定“几秒完成”。

建议状态：发现新版 → 下载 → 预检 → 待确认/已排期 → 排空请求 → 备份 → 切换 → 验证 → 成功 / 需要恢复。

**体验加分：** 一份“升级收据”记录操作者、源/目标版本、备份、迁移、健康检查与结果。安全地减少步骤，不隐藏停机。

### D. Recovery Vault｜备份不是一个绿色勾 · P1

**客户看到：** 最后一次备份、文件校验状态、最近恢复演练、可恢复范围，以及当前是否需要人工介入。

- “已备份”“校验通过”“恢复演练通过”分开显示；不要把上传了一个文件叫可恢复。
- 默认 SQLite 继续使用数据库备份接口与当前排空/停机边界，不直接复制正在写入的 WAL 库。
- PostgreSQL 使用独立的数据库原生备份/迁移流程；没有相应恢复证据时，不显示通用的一键可回退承诺。
- 镜像、宿主工具、配置与 schema 作为一组恢复身份；敏感备份加密，升级恢复点不被普通轮转自动删除。
- 有新业务写入后不自动拿旧备份覆盖；恢复到新目录、保留现场、完成必要对账，再决定切流。
- 只有能证明尚未接受新写入且 schema 向后兼容时，才讨论自动切回旧镜像；否则明确进入恢复流程。

**体验加分：** 给客户恢复路线和证据，而不是一个可能丢数据的“回滚”按钮。

### E. Control Room｜独立运维底座与自助诊断 · P1

**客户看到：** 实例健康、监听/就绪状态、磁盘风险、备份与升级进度，以及可预览的脱敏诊断包。

- 升级任务由独立于网关进程的宿主 Operator 执行并持久记录；不能让正在被重启的网关负责重启自己。
- 网关容器不直接挂载 Docker socket。Operator 属于高权限边界，使用本地受限通道、命令白名单、实例绑定与独立审批，不提供任意 shell。
- 验证镜像来源、发行签名/证明及发布者策略。现有 checksum/digest 是完整性基础，不应被宣传成已经具备发行签名；发布流水线需要配套升级。
- 操作身份、镜像 digest、计划有效期与幂等键绑定；安装目录、注册表与文件路径均做允许范围检查。
- 独立控制通道负责升级期间的状态；如果控制通道不可用，界面应诚实显示重连中。运维链路不能只依赖正在切换的 2099。
- 诊断默认仅元数据；导出前可预览，禁止包含密码、令牌、原始配置、数据库或请求正文。上传支持团队必须再次选择并确认。

**体验加分：** 用户知道系统现在处于什么阶段、谁在负责、出了问题下一步做什么。

### F. Fleet Console｜企业治理与批次发布 · P2，可选

- 独立实例管理员与工作空间管理员分权；计价管理权限不等于宿主机升级权限。
- 审批、维护窗口、审计导出、分批更新、暂停批次和失败阈值。
- 内部验证 → 经单独授权的本机 2099 → 试点客户 → 扩大范围，不把发布动作直接等同于切换现网。
- 离线客户可导入经过验证的升级包；可选 Fleet 仅在明确加入后连接，网关处理请求不依赖中心在线。
- 多实例滚动更新是后续专项：需要流量排空、兼容 schema 与共享状态设计；不把两套容器同时写同一 SQLite 文件称为零停机。

## 04｜交互与视觉方向：fancy，但不花哨

- 延续 SiftGate 深绿色与既有官方 Logo（复用当前资源，不以通用盾牌替换），使用暖白底、大留白、细分隔线、明确状态和少量功能性动效。
- 首次体验采用任务式引导；登录页不是说明书，也不能是死胡同。
- 运维界面优先表达“可执行什么 / 为什么受阻 / 下一步是什么”，而非堆 CPU 小图表。
- 版本差异、停机与兼容性不藏在弹窗小字里；重大动作有可复述的确认摘要。
- 进度持久、可重连、可追溯。支持键盘、屏幕阅读器、七种语言与窄屏。
- 视觉稿明确标注“方案示意”，不能把静态演示当作已可操作的生产界面。

## 05｜分三批交付，不先造一个庞大的云平台

| 批次 | 优先交付 | 完成门槛 |
|---|---|---|
| P0：客户能自己进门 | 首次认领、设置凭据、密码来源帮助、登录错误本地化、受控恢复、清理明文日志 | 干净 Linux 安装无需询问初始密码即可安全激活；旧实例不被重新认领；管理会话撤销不影响调用 Key |
| P1：客户敢于升级 | Operator、安全升级中心、宿主工具更新、备份与恢复证据、维护状态、诊断预览 | 真实跨版本演练；掉电/断网/关闭浏览器后可恢复任务；新写入不被旧备份覆盖 |
| P2：企业可治理 | 独立管理身份深化、OIDC 策略、批次发布、审批、离线包、可选 Fleet | 权限隔离、批次暂停、中心断联不影响数据面；高可用另设验收 |

不要给尚未拆分验证的工作虚报工期，也不要把“后台加按钮”当作升级链路已经完成。

## 06｜必须过的十二条验收

1. 并发首次认领只能成功一次；激活码过期、重放、跨实例使用均拒绝。
2. 旧密码/SSO/恢复实例不重新开放认领；反复启动不会重置管理身份。
3. 日志、诊断、分析事件和普通 URL 中没有初始化码或长期密码。
4. 变更/恢复管理凭据后旧管理会话失效，原 Gateway API Key 与业务账目保持有效。
5. 七语言登录错误有可行动提示，未配置的恢复通道不会展示成可用按钮。
6. 非实例运维角色不能升级；工作空间管理员不能因此获得宿主权限。
7. 错误签名、错误架构、错实例、越界路径、低磁盘和不兼容版本在停机前拒绝。
8. 浏览器关闭、重复提交、Operator 重启不会制造两个升级任务或丢失任务状态。
9. 镜像/安装工具/Compose/schema 的组合被验证，不出现“新镜像 + 不兼容旧工具”的半升级。
10. 首次验证完成前有明确的请求隔离策略；候选一旦产生业务写入，不进行破坏性自动恢复。
11. 备份能在独立目录恢复并校验配置、时区、Key、日志与计价状态；SQLite 与 PostgreSQL 分别验收。
12. 改动在隔离环境验收；本机 2099 的任何切换仍需单独授权，地址与客户配置不得被顺带改变。

## 07｜评审建议

建议先批准 P0 + P1 的范围与安全边界，再拆成 Goal spec 和可独立验收的里程碑。P2 只预留协议和权限边界，不阻塞首批交付。

**核心判断：真正的 fancy，是客户不再需要猜密码、猜升级进度、猜备份能不能救回来。**
